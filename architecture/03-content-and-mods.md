# 03 — Content pipeline and moddability

> **Partly superseded by AD-39 and AD-40.** The pipeline, the overlay map, the one validator
> and Tier 1 are unchanged. §03.7's tier list is rewritten: the script tier is Lua, not ES
> modules, and a native plugin tier sits between it and the engine.

This document specifies how content is authored, shipped, discovered, validated,
overridden, and extended — by us, and by modders. It implements `AD-7` (content is
data), `AD-8` (two modding tiers), `AD-9` (conventional mod index), `AD-18` (asset
VFS), and `AD-22` (strings under `assets/`).

Platform facts used here are verified in the [README](README.md#what-the-platform-gives-us-and-what-it-forbids);
the load-bearing ones are restated in §03.1 because a mod system that ignores them
does not work.

## 03.1 The five platform facts that shape modding

1. **Mods are only reachable at `/mods/<id>/assets/*`**, and only when
   `serve_mods: true` and the mod is enabled
   (`launcher/internal/static/static.go:131-165`, FR-AST-11/12).
2. **A mod's `mod.manifest.json` is not reachable from the browser.** The data API
   exposes only `GET /api/data/config/mods`, which returns id, name, version,
   priority, enabled, and `missing_dependency`. There is no `GET /api/data/mods/*`
   route in the launcher.
3. **`/assets/*` serves only the base game.** FR-AST-12 assigns overlay resolution
   to the consumer, so the engine probes mod paths itself.
4. **Every base asset ships `mutable: true`** and asset hashes are advisory
   (`packaging/internal/pack/manifest.go:122`, FR-AST-4/7), so nothing in the base
   game is off-limits to an override.
5. **A mod cannot shadow `engine/` or `index.html`** — the server enforces it and
   the mod manifest schema rejects `^engine/` paths.

From (2) and (3): the browser can learn *which* mods are enabled but not *what is
in them*. Discovery must therefore be by a **conventional path inside `assets/`**,
which is `AD-9`.

## 03.2 Two resolution regimes, deliberately

Mixing these up is the single most common way a mod system becomes useless, so the
engine keeps them strictly separate.

| | Assets (bytes) | Content records (data) |
|---|---|---|
| Examples | `textures/*.png`, `audio/*.ogg`, `shaders/*.wgsl`, `models/*.glb` | items, powers, origins, sectors, NPCs, dialogue, quests |
| Override semantics | **File shadowing.** The mod's file at the same relative path wins outright. | **Record merge by id**, with an explicit `override` declaration. |
| Why | A texture is a whole artifact; replacing it wholesale is what the author means. | A mod that adds one item must not have to reproduce the base file it lives in. |
| Owner | `vfs` module (§03.4) | `ContentRegistry` (§03.5) |

If content were file-shadowed like assets, "add one pistol" would mean "take over
`data/items.json` forever and break on every game update". Explicit record merge is
what makes small mods survive patches.

`game/locales/` (the `/locales/*` route). `engine/` holds code and only code.

At M1 the shipped tree is `data/packs.json` plus `data/packs/*.pack.json`,
`locales/en.json`, `shaders/wgsl/quad.wgsl`, `textures/ui/frame.png` and
`ui/shell.css`. The base game's own mod-shaped index (`data/mod.json`) is not
shipped yet: nothing reads it until the mod manager lands in M4, and an unused
index is exactly the kind of dead file this architecture deletes rather than
documents.

Two rules are enforced by a build check before the packager runs: the `game/` root
contains exactly `index.html`, `shell.js` (and the packager's generated
`release.manifest.json`), and no file name contains anything outside
`[A-Za-z0-9._-]` per path segment (packaging rule 3).

### MIME types must be declared

`mimeFor` looks the extension up in `launcher.config.json`'s `mime_types` and falls
back to `application/octet-stream` (`launcher/internal/static/serve.go:185`). The
config merges over the built-in defaults rather than replacing them
(`Config.Parse` does `cfg := Default()` then `json.Decode(&cfg)`, and Go reuses a
non-nil map), so adding keys is safe. Worldspiracy's launcher config declares:

```json
"mime_types": {
  ".wgsl": "text/plain", ".gltf": "model/gltf+json", ".glb": "model/gltf-binary",
  ".ktx2": "image/ktx2", ".csv": "text/csv", ".md": "text/markdown"
}
```

`.wasm` (`application/wasm`) and `.js` (`text/javascript`) are already defaults and
must not be removed — `WebAssembly.instantiateStreaming` refuses any other type for
the wasm, and a wrong `.js` type will be blocked by CSP.

## 03.4 The asset VFS

One module, `engine/vfs.js`, is the only thing in the game that knows a URL. It is
the implementation of `AD-18` and FR-AST-12, and it resolves from a **map**, never by
probing.

The map was designed against FS §17.1's request budget (≤ 150 root requests at boot),
but note that **boot time is deferred and that budget is not gated** (`AD-25`). The map
stays because its justification does not depend on the budget: probing costs
`N_mods × M_assets` requests, so a player with three mods pays three times the request
volume for the same content and the cost grows every time they install another mod, and
the map is also what makes a mod's declared `overrides` auditable at publish time. It
is a design we would have to build later anyway, so we build it now and ship loose
files inside it.

**Build the map once, before the first asset request:**

```js
async function buildOverlay() {
  const base = await json('/assets/asset.manifest.json');       // base path set
  const mods = (await api('/api/data/config/mods')).available
                 .filter(m => m.enabled)                        // launcher is authoritative
                 .sort((a, b) => b.priority - a.priority || a.id.localeCompare(b.id));
  const map = new Map();                                        // path -> mod id
  for (const m of mods) {
    const idx = await json(`/mods/${m.id}/assets/data/mod.json`);   // 1 request per mod
    if (!idx) { report.skip(m.id, 'no_index'); continue; }
    for (const p of idx.overrides) map.set(p, m.id);
    for (const packPath of idx.packs) {
      const pack = await json(`/mods/${m.id}/assets/${packPath}`);
      for (const p of assetPathsOf(pack)) map.set(p, m.id);         // declared by the pack
    }
  }
  return { base, map };
}

// Resolution: exactly one request, ever.
function resolveUrl(path) {
  const mod = overlay.map.get(path);
  return mod ? `/mods/${mod}/assets/${path}` : `/assets/${path}`;
}
```

Properties and rules:

- **One request per asset. No probes, no expected 404s.** Total boot requests are
  `1 (asset manifest) + N (mod indexes and packs) + M (assets)`, which is what keeps
  the game inside the §17.1 budget as mods are installed. A probing implementation
  would cost `N_mods × M_assets`; with three mods and 150 assets that is 450 requests,
  and it gets worse the more the player mods the game — precisely backwards.
- **The declaration is auditable.** Because resolution is map-based, a mod's index
  must declare what it provides. The validator cross-checks the index against the
  mod's actual `assets/` tree and reports `undeclared_override` at publish time
  (§03.9), so a forgotten declaration is a caught mistake, not a silent non-override.
- **`enabled` from `/api/data/config/mods` is authoritative**, including a mod the
  launcher disabled for a `missing_dependency`; the engine never second-guesses it.
- **Everything, including shaders and UI data, is fetched through `vfs`.** A
  hardcoded `/assets/...` URL anywhere is a bug and is caught by a lint rule.
- **`vfs.manifest` wraps `assets/asset.manifest.json`.** Its hashes are used for
  change detection, cache keys, and reporting — never to refuse a load (FR-AST-4).
- **The API is bundle-oblivious.** The manifest schema reserves `bundles`
  (FR-AST-10) which the packager does not emit today
  (`packaging/internal/pack/manifest.go` has no bundle path). When it does, only
  `vfs` gains a bundle reader — and that is also the fix for content that grows past
  the request budget.
- **`/locales/*` is fetched directly**, bypassing the overlay, because mods cannot
  shadow it (AD-22). Game strings live in `assets/locales/` and *do* go through
  `vfs`.

**The load document, as built at M1.** The worker assembles the map and the pack
list and hands the core **one** document, `worldspiracy.content-load/1`: each pack
carries `source` (`base` or a mod id), `priority`, `pack`, `kind`, `path`,
`engine_min`, its `records`, and — for a mod — the index's declared `overrides`
and, where the caller knows the file list, the pack's `assets`. The core merges,
applies the structural rules, validates, and returns a
`worldspiracy.load-report/1` (`{ok, packs, skipped, record_count, items,
rules_hash, presentation_hash}`, with each item a `{severity, code, path, args}`).
The document shape is typed in `src/web/shared/content.ts`; the **merge order and
the semantics are the core's**, not the loader's (`01:01.2`). One consequence
worth stating because it broke the dev loop once: `assets/asset.manifest.json` is
generated by the **packager**, so a release has it and the `make play` dev tree
does not. It is therefore **optional at load** — a warning, not a failure. It is
the validator's base-asset list for the `undeclared_override` cross-check and,
later, the cache key; neither is needed to resolve a URL, because the overlay map
comes from mod indexes and the base pack list is `data/packs.json`. An M1 reading worth
recording: the hand-off is JSON rather than a packed struct, because the core
already parses JSON for commands, previews and saves, and a second encoder would
be a second format to keep in step. The seam is "one document in, one registry
and one report out", and a binary encoding is a later change behind it.

## 03.5 Content packs and the record merge

A **content pack** is one JSON file holding a list of typed records. Packs are the
unit of authoring, review, and mod distribution.

```json
{
  "schema": "worldspiracy.content-pack/1",
  "pack": "wsp.core.gear",
  "kind": "content",                    // "content" | "presentation" (AD-29)
  "engine_min": "0.1.0",
  "strings": "locales/gear",            // optional: a string table this pack owns
  "records": [
    { "id": "wsp.item.pistol",  "type": "item",   "data": { "…": "…" } },
    { "id": "wsp.item.rifle",   "type": "item",   "data": { "…": "…" } },
    { "id": "wsp.origin.robot", "type": "origin", "data": { "…": "…" } }
  ]
}
```

The base game's `assets/data/packs.json` lists its packs in load order. Each
enabled mod's index lists its packs. The registry then applies, in order: base
packs → mods ascending by `priority` (ties by id ascending, so the highest priority
is applied last and wins).

Merge rules, checked by the validator and reported per mod:

| Case | Result |
|---|---|
| New id | Added. |
| Id already present, record has `"override": true` | Replaces the earlier record. Recorded in the load report with both sources. |
| Id already present, no `override` | **Error for that mod.** The mod is disabled with `duplicate_id` naming both sources — it never silently clobbers. |
| Record has `"remove": true`, `override: true` | Removes the record. Only permitted for non-structural types; structural removals are a load error. |
| Id not namespaced under the owning pack | Error (`bad_namespace`). Every id is prefixed with its pack id, so two mods cannot collide by accident. |

**Structural types** (`ladder`, `trait_order`, `dice_vocab`, `effect_op`) and the rules
pack's **granularity fields** (`tile_mm`, `legacy_sector_tiles`, `02:02.6`) may not be
overridden or removed by a mod at all. That is `AD-14`: the resolution table is not
moddable, because a save's meaning depends on it, and under `AD-33` the tile size is the
same kind of thing — changing it would invalidate every saved world and every other mod's
coordinates. Everything else — including every power, item, origin, sector, quest and
dialogue node — is moddable.

The **distance parameters** split along that same line (`02:02.6`). A mod may retune
movement, weapon ranges and the per-distance steps — 4C adapted to a vision is exactly what
the content model exists for — but not the tile size or the legacy-sector conversion.

**The record types, as shipped at M3.** The table is the whole vocabulary; a pack that
names anything else is refused with `bad_record_type` rather than ignored, because a
record nothing reads is a record whose author believes something false.

| Type | What it is | Read by |
|---|---|---|
| `ladder`, `trait_order`, `dice_vocab`, `effect_op` | **Structural**: not moddable (`AD-14`). | `02:02.2` |
| `rules` | The rules pack's own blocks: granularity, distances, elevation, cover, creation, generation and skill tables (`02:02.6`). | `l0`, `l1`, `l2`, `l4` |
| `item` | Equipment: hands, melee kind, reach, damage, armour, modifiers, tags, and now `slot`, `price` and `kind` (`AD-29` rule 3). | `l1::items`, `l4::economy` |
| `skill` | A named row-step bonus and the action tags it applies to (`4c:275`). | `l1::skills` |
| `power` | An effect-DSL template (`AD-16`). | `dsl` |
| `origin` | The six canonical modifiers of `4c:124-131`. | `l1::character` |
| `character` | An authored sheet: NPCs, adversaries, the editor's template. | `l1::character` |
| `vehicle` | The three Vehicle Traits and their records (`4c:1300-1365`). | `l2::vehicle` |
| `outcome_table` | The four-colour effects for one action (`02:02.5`). | `l2::actions` |
| `sector_map` | A tile map: dimensions, and per-tile level, blocking height, terrain and material (`02:02.12`). | `l3::world` |
| `encounter` | A map, party spawns, enemies, and now `on_win`/`on_loss`/`epilogue` bindings. | `l2::encounter` |
| `world` | A **generated region**: the generator's parameters, the authored maps overlaid on it, the arrival point, the start hour, and the stations (`02:02.6`). | `l3::gen`, `sim` |
| `faction` | Standing bands, a default standing, and `reaction_polarity` (`02:02.6`, `D4`). | `l4::factions` |
| `dialogue` | A node graph: nodes, options, `when` conditions, `check`s and effects (`02:02.7`). | `l4::dialogue` |
| `quest` | Steps with entry and completion conditions and effects, plus completion bindings. | `l4::quests` |
| `shop` | A merchant's stock, the item kinds it buys, and its margin (`02:02.7`). | `l4::economy` |
| `signal` | A **named condition** the engine evaluates for UI gating (`09:09.4`). Presentation: readable by a layout, never an input to resolution. | the engine, the shell |
| `visual`, `string_table` | Presentation: merged and hashed, never interpreted (`AD-29`). | `vfs`, the shell |

A `world` record and a `sector_map` are not the same thing, and the difference is
`02:02.6`'s decision made concrete: a `world` **generates** terrain from a seed and
treats an authored map as an override at an origin, while a `sector_map` that no world
record names is **authored outright** and is its own baseline. Both go through one delta
path, so a save's world half is the same shape either way.

**Two identities, not one (`AD-29`).** After the merge the registry computes:

- **`rules_hash`** — the structural tables plus every rules-bearing record. This is what
  a save binds (`AD-11`), and a mismatch is a hard, explained refusal, because the save's
  meaning depends on it.
- **`presentation_hash`** — visual descriptors, string tables and their assets. A change
  here is recorded in the load report and the save header and **never** invalidates a
  save or blocks a load.

That split is what makes a cosmetic pack safe to try: a 3D character pack, a reskin, or a
translation can be enabled, compared and disabled without any save ever being reported as
mismatched. It also lets a pack be applied **partially** — the party but not the
townsfolk — because the descriptor is per record.

**Pack kinds.** A pack declares `kind: "content"` or `kind: "presentation"`. A
presentation pack may define visual descriptors, strings and assets; it **may not** define
a rules record, and the validator rejects one that tries (§03.9). One pack cannot be both,
so "does enabling this change my game or only my game's looks?" is answerable from the
manifest alone — which is exactly the question the mod manager has to answer for the
player.

## 03.6 Mod anatomy

```
data/mods/<id>/
├── mod.manifest.json              # REQUIRED by the launcher; not reachable from the browser
└── assets/                        # the ONLY subtree the launcher will serve
    ├── data/mod.json              # REQUIRED by US: the conventional index (AD-9)
    ├── data/packs/*.pack.json     # this mod's content packs
    ├── locales/<lang>.json        # this mod's strings
    ├── textures/…  audio/…  shaders/…  models/…   # asset overrides and additions
    ├── ui/*.layout.json  ui/*.js  ui/*.css        # layout, renderers, theme (09)
    └── scripts/*.js               # Tier-2 hooks (optional, AD-8)
```

`mod.manifest.json` is the launcher's contract: `schema`, `id`, `name`, `version`,
`assets[]`, plus `priority`, `requires`, `conflicts`, `base_release`,
`requires_engine`, `expected_base_hash`. Full detail in
`architecture/schemas/mod.manifest.schema.json`. Its `assets[].path` values are
informational for diagnostics; the launcher serves any file under
`/mods/<id>/assets/` for an enabled mod.

The mod's own index — `assets/data/mod.json`, written by the editor — is *ours*:

```json
{
  "schema": "worldspiracy.mod-index/1",
  "id": "noir-overhaul",
  "name": "Noir Overhaul",
  "mod_api": "worldspiracy.mod/v1",
  "engine_min": "0.1.0",
  "packs": ["data/packs/noir-gear.pack.json"],
  "scripts": ["scripts/on-hit-hooks.js"],
  "ui": {
    "api": "worldspiracy.ui/v1",
    "theme": "ui/noir.css",
    "entries": [
      { "id": "character", "mount": "panel.character", "projection": "roster",
        "layout": "ui/character.layout.json", "renderer": "ui/character.js",
        "commands": ["advance_trait"], "priority": 10 }
    ]
  },
  "overrides": ["textures/ui/noir-frame.png", "ui/character.layout.json", "ui/noir.css"],
  "requires_content": { "wsp.core.gear": ">=1" },
  "notes": "Adds 12 items, reskins combat UI, and replaces the character sheet."
}
```

The `ui` block is the moddable interface (`09`): a **layout** is presentation data, a
**renderer** is an ES module with a capability object, and a **theme** is CSS custom
properties and a stylesheet. Every UI file is declared in `overrides` like any other asset —
that list is what the VFS resolves from, so an undeclared file is silently never applied.

`overrides` is **required for correctness**, not informational: the VFS resolves from
this list (`AD-18`, §03.4), so an asset that is not declared is not overridden. The
editor writes the list automatically from the project, and the validator cross-checks
it against the mod's `assets/` tree (§03.9), so the failure mode is a publish-time
error rather than a silent one. It is also what lets the mod manager show a conflict
report *before* anything is enabled.

## 03.7 The modding tiers

| Tier | Ships | Can | Cannot | Who writes it |
|---|---|---|---|---|
| **1 — Data** | packs, locales, assets | add/replace items, powers (via DSL), origins, sectors, NPCs, dialogue, quests, UI data, balance; translate; reskin | change the resolution table; add new effect primitives; change the engine | a writer or designer with a text editor |
| **2 — Script** | Tier 1 + `scripts/*.js` | register hooks, implement effects the DSL cannot express, drive quest logic and AI | change the resolution table; reach the network; allocate GPU resources; affect a save without being recorded in it | someone comfortable with JS |
| **3 — Engine** | a new `game.wasm` | anything | — | us only; **not a supported mod** |

Tier 3 is listed to be explicit that **there is no mod-wasm path**. Reasons: the CSP
allows it (`wasm-unsafe-eval`), but a mod-wasm would need its own reviewed ABI, its
own save-compatibility story, its own cross-platform determinism story, and it
would multiply the support surface for the benefit of a vanishingly small number of
authors. If demand appears, the right answer is to extend the Tier-2 script API, not
to open the core.

### The two Tier-2 execution contexts

A Tier-2 mod ships two different kinds of JavaScript, and they run in two different places
with two different contracts (`09`):

| Context | Ships | Runs in | Contract |
|---|---|---|---|
| **Simulation** | `scripts/*.js` | the engine worker, beside the sim | deterministic; hooks answer synchronously; no DOM; its hash is recorded in the save (`AD-8`) |
| **Interface** | `ui/*.js` | the page, on the main thread | DOM access through a capability object; **no** determinism contract; cannot touch state except by posting a command, which the shell scopes and mediates |

They are not interchangeable, and the difference is the point. A simulation script can change
what a roll resolves to and is therefore recorded in the save; a UI renderer can only change
what the player sees and can therefore be removed without invalidating anything (`AD-36`).
A UI renderer is never given a wasm handle — the page does not have one (`AD-4`) — so its
only route to the world is the command stream.

### Tier-2 script API

Scripts run **in the engine worker**, alongside the sim and the renderer, because
hooks must be synchronous: the core asks for a modifier during resolution and needs
an answer now. The core imports one function from JS:

```rust
// wasm import, implemented by worker.js as a dispatcher into the hook table
fn wsp_script_hook(hook: u32, ctx_ptr: u32, ctx_len: u32) -> u64;  // (ptr << 32) | len
```

A script registers pure functions:

```js
Worldspiracy.register('worldspiracy.mod/v1', {
  hooks: {
    modify_damage({ attacker, target, attack, damage }) {
      if (attack.tag !== 'melee') return damage;
      return damage + 5;                       // integers only
    },
    on_hit({ attacker, target, colour, rng }) {
      if (colour === 'Yellow' && attacker.hasPower('wsp.power.piercing-strike')) {
        target.applyStatus('stunned', { panels: 1 + (rng.d100() % 10) });
      }
    },
  },
});
```

The `ctx` object is a **read-only snapshot plus a command queue**: reads are
synchronous views over the sim, writes are queued commands applied by the core after
the hook returns. That is what keeps a script from tearing a resolution in half, and
it means the core validates every write a script asks for.

The contract, stated for modders and enforced by the replay harness:

- integers only on anything state-visible; no `Date`, no `performance`, no
  `Math.random` (the API's `rng` is the seeded stream);
- no `fetch`, no `localStorage`, no `indexedDB` (CSP blocks the first; the others
  are dishonest for save state — FR-API-1);
- no DOM, no timers — a hook that schedules work has broken the model;
- scripts are hashed and recorded in the save's `meta`; a replay that differs
  because of a script is reported with the script named.

A script that throws is disabled for the session, the hook is skipped, and a
diagnostic is emitted. A script cannot take down the boot.

**As built.** The Rust half is `crates/kobra-core/src/script.rs`: the `wsp_script_hook`
import (wasm only), the frozen context document — which carries the hook's
incoming value, the entities and the attack, and **no RNG** — the queue, and
`wsp_script_record`/`wsp_script_report`. The worker half is
`src/web/worker/scripts.ts`: the `Worldspiracy` global, the `worldspiracy.mod/v1`
registry, the hook dispatcher, and the loader that fetches each declared script,
hashes it, and imports it. The loaded set and its hashes go into the save's
`meta.scripts` (`AD-8`).

Four decisions differ from the sketch above, each for the determinism contract:

- **There is no `rng`.** A script that drew would make the draw order depend on
  script code, which is what `02:02.9` rule 3 forbids. A script that needs a die
  declares one in an effect (`{"apply_status": {"id": "stunned", "panels":
  {"dice": "1d10"}}}`) and the core draws it in the fixed order every other effect
  uses.
- **The answer is compiled by the DSL's own compiler** (`dsl::resolve_effect`), so
  a script cannot name an effect a data mod cannot — which is what makes "Tier 1
  plus a script" a strict superset rather than a second system. Writes are
  `HookEffect`s the core applies and validates, never direct mutation.
- **A script hook runs only for an entity that carries a power**, because a script
  extends a power rather than replacing the engine. That keeps scripts off a path
  that has nothing for them to modify — including the defensive hooks, which run
  for the *defender's* powers, so a `resist` script needs the entity being
  attacked to hold one.
- **The script hook set is the kernel hook set minus `on_acquire` and
  `modify_trait`.** Those two change a *plan* or a stored floor rather than
  queuing a write, so a script reaches their effect through queued commands
  (`boost_trait`, `modify_trait_steps`, an acquisition record) instead. Shipping
  a hook the engine never consults would be a promise the ABI does not keep; the
  other ten — `modify_attack`, `modify_damage`, `modify_armor`, `movement`,
  `action_economy`, `hit`, `resist`, `own_turn`, `absorb`, `power_used` — are all
  consulted, and `crates/kobra-core/tests/scripts.rs` proves it for the two that are easy
  to leave unwired (the economy multiplier and the colour override).
- **A script whose declared hash does not match its text is skipped, not run.**
  `AD-8` records the hash in the save so a replay can name the script that
  changed, and a hash that lies defeats that; the editor is where a stale
  declaration is a publish-time error.
- **The report reaches the shell, with the detail that makes it actionable.** The
  worker posts `worldspiracy.script-report/1` and the shell renders it in the
  development sidebar (`09:09.11`): a registered script with the hash the save
  binds, a disabled script with its reason, and a failure with its detail — the
  declared-versus-expected API for `api_mismatch`, the thrown message for `threw`.
  A code alone tells a modder that something broke, not what.

On a native build there is no import, so no host is installed unless one is: a
host-side test installs the production `ScriptHost` seam and drives the real
dispatch, compile and command-queue path through a resolved encounter
(`crates/kobra-core/tests/scripts.rs`), and the node tests drive the worker's dispatcher.

## 03.8 Load sequence at boot

```
1. GET /api/state                     → api_version, engine_version, save_version, data_writable
2. GET /api/data/config               → settings
3. GET /api/data/config/mods          → { enabled:[ids], available:[{id,name,version,priority,enabled,missing_dependency}] }
4. vfs: GET assets/asset.manifest.json
5. for each enabled mod, in priority order:
      vfs probe /mods/<id>/assets/data/mod.json   → index, or skip with a report
6. build the load list: base packs (from assets/data/packs.json) + mod packs
7. wasm: wsp_validate_content(load list)  → report
      any pack with errors is dropped; its mod is disabled (fail-soft, FR-AST-13)
8. wasm: wsp_new_campaign(config) | wsp_load(save)
9. register Tier-2 scripts; hash them into the session
10. start the worker loop; begin heartbeat (FR-SRV-18)
```

Every step is reported to a **content load report** available in the UI and in
`/__kobra/diagnostics` (which already includes the mod list). The report is the
support artifact: mod id, version, what loaded, what was skipped, and why.

Dependency handling follows the launcher: a mod whose `requires` are unsatisfied
arrives from `/api/data/config/mods` with `missing_dependency` set and `enabled:
false`; the engine must treat `enabled` as authoritative and never try to load it.
`conflicts` are the launcher's informational field and become a warning in the
report, not a refusal.

## 03.9 Validation

`AD-15`: one validator, in wasm, called by the game at load and by the editor before
it saves or publishes. It is reported as data, never as an exception:

```json
{ "ok": false,
  "items": [
    { "severity": "error", "code": "unknown_ref",
      "path": "data/packs/noir-gear.pack.json#/records/4/data/grants_power",
      "args": { "ref": "wsp.power.fireball", "did_you_mean": ["wsp.power.fire-bolt"] } },
    { "severity": "warning", "code": "balance_outlier",
      "path": "…#/records/9/data/damage", "args": { "value": 90, "p99": 25 } }
  ]}
```

Rules the validator enforces beyond shape:

1. Every `type` is known, every id is namespaced, every structural field is present.
2. Every reference resolves **after the merge**, not before — so a mod may
   reference a base record and a base record may not reference a mod record.
3. An `override` replaces a record of the same `type`; changing a record's type is
   an error.
4. Every DSL trigger/condition/effect is known, its operand types are checked, and
   every dice term is legal.
5. Every string id referenced exists in the string tables; missing strings are
   warnings, because partial translation is allowed.
6. A **`kind` violation**: a pack declared `presentation` that defines a rules-bearing
   record type, or a pack declared `content` that defines only visuals. The rule exists so
   that a cosmetic pack can never silently change balance or invalidate a save (`AD-29`).
7. **An `undeclared_override`**: a file under the mod's `assets/` whose path shadows
   a base asset but which the mod's index does not declare. This is an *error*, not a
   warning, because the VFS would silently never apply it (`AD-18`) — a mod that
   appears to do nothing is the worst failure mode a mod system can have.
8. Balance outliers are warnings derived from the content's own distribution
   (a damage value beyond the 99th percentile of its class), so the check stays
   useful as balance changes. Never a hard error.
9. A pack that declares `engine_min` above the running engine is skipped whole,
   with a message, rather than half-loaded.
10. A **structural record that disagrees with the build**: the `ladder` record's
    variant must equal the ladder compiled into the wasm, and `trait_order` must
    equal the engine's trait order. Structural content is not moddable (`AD-14`),
    so a disagreement is a package that would resolve rolls differently from the
    table in the binary, and it is an error rather than a tunable.
11. **A UI declaration that cannot work** (`09:09.5`): a layout key outside the vocabulary,
    a path into a projection the entry does not subscribe to, a `text-key` that does not
    exist, a `when-signal` no `signal` record declares, an `action` outside `02:02.13`'s
    vocabulary, a `commands` scope outside the command vocabulary, a renderer or layout file
    not declared in `overrides`, or a `ui.api` major the shell does not speak. At publish
    these are errors; at mount they are fail-soft per node and per entry. The wasm pass is
    `wsp_check_ui`, which takes the layout documents and the mod's `overrides`/`assets` and
    returns the same `{severity, code, path, args}` items the rest of the validator does.

**Where the file list exists.** Rule 7 needs a mod's actual `assets/` tree, and a
browser cannot enumerate one. So the check runs where the list is known — the
editor at publish time, and the dev loader — and is silent at runtime rather than
wrong; the validator's `check_overrides` reads the per-pack `assets` array when
the caller supplies it, and `check_ui` reads the same list for a pack's layout,
renderer and theme files. At runtime the map is the enforcement: an undeclared
file is simply never resolved. That is exactly why the publish-time verdict is an
*error* and not a warning.

## 03.10 What a mod can never do

Stated as guarantees, each with its mechanism — this list is what makes it
reasonable to say "install mods, they are trusted":

| Cannot | Mechanism |
|---|---|
| Fetch or transmit anything | CSP `connect-src 'self'` (FR-SRV-17) |
| Shadow engine code or the page | Server refuses mod paths outside `assets/`; manifest schema rejects `^engine/` |
| Write to the player's disk outside `data/` | The data API writes only validated slots, whitelisted settings groups, and tar.zst mod dirs |
| Delete the player's data | Launcher moves to `.trash-<ts>/`, never unlinks (FR-SHELL-4) |
| Change the rules of resolution | Structural content types are not overridable (AD-14) |
| Break a save silently | `content_hash` + mod list recorded in the save; a mismatch is reported |
| Prevent the game from booting | Every content failure is per-mod and fail-soft (FR-AST-13) |

What it *can* do, honestly: run arbitrary same-origin JS in the worker and therefore
corrupt its own session, produce a bad pack, or crash the worker. A Tier-2 mod that ships a
**UI renderer** goes further, and the difference is stated rather than implied: its code runs
**on the page**, so it can read the DOM, read the launcher's diagnostics, and call the
launcher's same-origin data API with the session cookie — including saves and the mod list
(`09:09.10`). CSP (`connect-src 'self'`) still keeps it off the network. That is the
platform's documented residual risk (FS §14, threat T14) and the mitigations are the
capability object, a declared command scope defaulting to read-only, per-entry isolation,
and a mod manager that says what a pack declares before it is enabled: recovery rather than
prevention, exactly as for a simulation script.

## 03.11 Mod manager and the author loop

**In-game mod manager** (a mode of the shell UI) reads
`GET /api/data/config/mods`, renders the enabled/available list with a conflict and
override report, and calls `POST /api/mod {id, action: install|enable|disable}` and
`DELETE /api/mod/{id}`. Enable/disable writes `data/config/mods.json`, which is
applied at boot (FR-AST-13) — so the manager must tell the player that enabling a
mod takes effect on the next launch, or restart the worker with the new set. The
second is better UX and is supported: the engine re-runs §03.8 without reloading the
page, falling back to a reload only if the content change is structural.

**Author loop.** `kobra-pack dev` serves a source tree without packaging
(`docs/authoring-a-game.md`), and `make -C launcher run-dev GAME=…` runs the
launcher against an arbitrary folder. Because the editor's project format is the
pack format, the loop is:

```
edit in the editor  →  Publish (installs into data/mods/<id>)  →  enable  →  playtest
     ↑                                                                    │
     └──────── edit the pack files in a text editor, reload (dev only) ───┘
```

Hot reload is `GET /__kobra/watch` (SSE), which exists **only in a dev build**
(FR-AST-14/15); release builds reload by re-running the load sequence, which is a
second-scale operation and acceptable outside development.
